# CarShare AI — Implementation Guide

A conversational car rental assistant built with React, Ollama (local LLM), and the Model Context Protocol (MCP). Users can search for cars, book rentals, and manage trips through natural language — all running locally at zero cost.

## How It Works — Step by Step

### 1. User sends a message

The React frontend calls `POST /api/chat` on the agent backend with:
```json
{
  "messages": [{ "role": "user", "content": "Find me a Lada" }],
  "sessionId": "abc-123"
}
```

The `sessionId` is a UUID generated once per browser session (stored in `sessionStorage`). It identifies the user's OAuth token in the MCP server's token store.

---

### 2. Agent backend opens an SSE stream

`index.ts` immediately sets response headers to `text/event-stream` and starts flushing events to the browser. This is what enables real-time streaming — the HTTP connection stays open and events are pushed as they happen.

```
event: token
data: {"token": "I"}

event: token
data: {"token": " found"}

event: tool_call
data: {"name": "listAvailableCars", "input": {...}}

event: tool_result
data: {"name": "listAvailableCars", "result": "..."}

event: done
data: {}
```

---

### 3. MCP client connects

`mcp-client.ts` creates one `Client` per `sessionId` (cached for the session lifetime). On first use it performs the MCP handshake:

```
Agent → POST /mcp  { initialize, protocolVersion, capabilities }
MCP   → 200        { serverInfo, mcp-session-id: "xyz" }
Agent → POST /mcp  { initialized }   ← confirms handshake complete
```

The OAuth `sessionId` is passed as `x-oauth-session-id` header — **not** as `mcp-session-id`. This distinction matters: `mcp-session-id` is the MCP transport's own session tracking (generated by the MCP server). Using your OAuth session ID as the MCP session ID caused the "Server not initialized" error because the MCP server couldn't find it in its transport map.

After connecting, `getMcpTools()` calls `listTools()` to fetch the 4 tool definitions (name, description, JSON schema) and converts them to Ollama's tool format.

---

### 4. The agentic loop

`agent.ts` runs a loop of up to 8 rounds:

```
Round 1:
  Send messages + tool definitions → Ollama (streaming)
  Collect text tokens → emit SSE "token" events → browser renders in real time
  Collect tool_calls from final chunk

  If no tool_calls → done, break

  For each tool_call:
    Emit SSE "tool_call" event → browser shows tool panel
    Call MCP server → get result
    Emit SSE "tool_result" event → browser updates tool panel
    Append result to history

Round 2:
  Send updated history (now includes tool results) → Ollama
  Ollama reasons over the results and either:
    a) Returns final text answer → done
    b) Calls more tools → loop continues
```

This is how multi-step tasks work. "Find the cheapest car and book it" causes two rounds: round 1 calls `listAvailableCars`, round 2 calls `bookCar` with the UUID from the result.

**Why a loop and not one call?** Ollama (like all LLMs) can only return one response at a time. It doesn't execute tools itself — it says "I want to call X with args Y" and stops. The loop is what bridges the gap: execute the tool, feed the result back, let the model continue.

---

### 5. Tool execution on the MCP server

When the agent calls `client.callTool({ name, arguments })`, the MCP SDK sends:
```json
{ "jsonrpc": "2.0", "method": "tools/call", "params": { "name": "listAvailableCars", "arguments": {...} } }
```

The MCP server receives this and runs the registered handler. The handler uses `oauthSessionId` (captured at session creation time as a closure) to call `getAccessToken(oauthSessionId)`, which returns a Bearer token, which is used to call the NestJS API.

```
Tool handler → getApiClient(oauthSessionId)
            → getAccessToken(oauthSessionId)   ← reads from in-memory token store
            → axios.get('/cars', { headers: { Authorization: 'Bearer ...' } })
            → NestJS API
```

The `oauthSessionId` closure is the key architectural decision: each MCP server instance (created per MCP session) has one fixed OAuth session baked in. All tools in that instance use the same user's token automatically.

---

### 6. SSE stream reading in the browser

`useChat.ts` reads the SSE stream manually using the Fetch API and a `ReadableStream` reader (not `EventSource`, because `EventSource` doesn't support POST requests):

```ts
const reader = res.body.getReader();
while (true) {
  const { done, value } = await reader.read();
  // decode chunks, split by \n, parse event/data pairs
}
```

Each event type updates React state differently:
- `token` → appended to the last assistant message's `content` (causes re-render → streaming text effect)
- `tool_call` → pushes a `ToolEvent` with `type: 'call'` onto the message's `toolEvents` array
- `tool_result` → pushes a `ToolEvent` with `type: 'result'`, paired with the preceding call
- `done` → sets `streaming: false`, removes the blinking cursor

---

### 7. Tool panel rendering

`ToolCallPanel.tsx` receives the `toolEvents` array and pairs up calls with results:

```
[call: listAvailableCars] [result: listAvailableCars]  → one panel
[call: bookCar]           [result: bookCar]             → another panel
```

Each panel shows: tool name, status badge (running / done / failed), and a collapsible body with the raw input JSON and output JSON. This gives full transparency into what the AI actually did — you can see the exact UUID it passed to `bookCar`, the exact response from the API, etc.

---

### 8. OAuth flow

When a tool returns "No tokens found for session", the frontend detects it and shows a "Connect account" button. Clicking it opens a popup to `/oauth/start?sessionId=abc-123`, which redirects to the NestJS API's OAuth authorization URL. After the user logs in, the NestJS API redirects to `/oauth/callback`, which stores the token in the MCP server's in-memory token store keyed by `sessionId`. The popup closes, and subsequent tool calls find the token.

## Running the Full Stack

You need 4 terminals:

```bash
# Terminal 1 — NestJS API
cd CarSharing/api && npm run start:dev

# Terminal 2 — MCP server
cd CarSharing/mcp && npm run dev

# Terminal 3 — Agent backend
cd CarSharing/agent && npm run dev

# Terminal 4 — React frontend
cd CarSharing/frontend && npm run dev
```

Open http://localhost:5173. Click "Connect account" on first use to complete OAuth.

## Models That Support Tool Use

| Model | Size | RAM | Quality |
|---|---|---|---|
| `qwen2.5:3b` | 2 GB | 4 GB | basic |
| `llama3.1:8b` | 4.7 GB | 8 GB | good |
| `qwen2.5:7b` | 4.4 GB | 8 GB | **best for tools** |
| `qwen2.5:14b` | 9 GB | 16 GB | excellent |

`qwen2.5:7b` follows tool-use instructions more reliably than `llama3.1:8b` at the same size. Avoid 1B/3B models for anything involving multi-step tool chains.

## Known Limitations & Fixes Applied

### "Server not initialized"
Caused by passing the OAuth `sessionId` as `mcp-session-id`. Fixed by letting the MCP server generate its own session ID and passing OAuth identity as `x-oauth-session-id`.

### Model passing `"null"` strings for optional params
Smaller models pass `"null"`, `""`, or `0` for optional fields. Fixed by sanitizing args in `callMcpTool` before sending to MCP:
```ts
const cleanArgs = Object.fromEntries(
  Object.entries(args).filter(([, v]) =>
    v !== null && v !== undefined && v !== 'null' && v !== 'undefined' && v !== ''
  )
);
```

### Model hallucinating bookings
Model would say "Your Lada has been booked" without calling `bookCar`. Fixed via system prompt: require explicit user confirmation before calling mutating tools, and never confirm an action unless the tool returned success.

### Model passing descriptions instead of UUIDs
Model passed `"ID of the 2000 Lada"` as `carId`. Fixed via system prompt: always copy the exact UUID from tool results, show the UUID in confirmation messages so the user can verify.

### API shape mismatch
`bookCar` was sending `startDate`/`endDate` but the NestJS API expects `hours`, `pickUpLocation`, `dropOffLocation`. Fixed by reading the actual DTOs and updating the tool schema to match.
